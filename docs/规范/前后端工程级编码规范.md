# 前后端工程级编码规范

本文档用于约束 AI 和开发者在前端、后端与 TypeScript 项目中输出健壮、可维护、可扩展、安全且可验证的工程代码。它不是框架风格大全，不替代具体项目自己的技术栈约定、目录结构、lint 配置、业务规则或接口文档。

涉及代码设计取舍时，先按《代码设计原则》判断 KISS、YAGNI、DRY、关注点分离、高内聚低耦合和最小惊讶原则；本文只展开前端、后端、TypeScript、API、安全和验证层面的工程检查。

采用边界：

- 只吸收跨项目、跨技术栈稳定成立的工程规则。
- 不完整搬运任何外部规范，不引入组织特定、平台特定或框架特定条款。
- 能交给格式化、lint、类型检查或安全扫描的规则，优先落到工具配置；本文只保留开发者和 AI 协作时需要主动判断的部分。
- 本文与其他项目规则冲突时，按根目录 `AGENTS.md` 定义的优先级处理；外部公开规范只作为本文维护依据，不高于用户已确认事实、当前唯一需求载体或项目既有规范。

## 总目标

工程级代码必须优先满足业务正确、边界清晰、错误显式、安全可靠、易于验证和长期可维护。不得为了快速实现而牺牲类型安全、接口契约、权限边界、错误处理、测试覆盖或可读性。

适用要求：

- 改动前先识别目标行为和非目标不变式；未被要求改变的接口、数据、权限、错误语义、性能和兼容性默认保持不变。
- 前后端实现应沿用项目既有错误模型、状态管理、数据访问、接口调用和验证方式。
- 任何真实失败都必须显式暴露，不用默认值、空对象、mock、旧链路或跳过检查掩盖。

## 工程级代码检查项

工程级前后端代码不是只跑通主流程，而是能覆盖真实输入、真实依赖、真实权限、真实状态和真实验证。AI 输出前后端代码时，必须把“健壮、可扩展、易维护、安全”转化为具体设计、实现和验证，而不能只在说明中声称已满足。

### 健壮性

健壮代码能在输入异常、依赖失败、并发冲突、重复请求、权限不足和状态不一致时保持行为可预测。

适用要求：

- 每个外部入口都必须明确正常路径、失败路径、边界值和不可恢复错误。
- 输入缺失、类型错误、格式错误、越权访问、资源不存在、状态冲突和外部依赖失败必须区分处理。
- 调用数据库、缓存、队列、文件系统、对象存储和第三方 API 时，必须考虑超时、重试、幂等、部分成功和回滚边界。
- 关键状态变更必须能确认最终结果；不能因为本地函数返回成功就假定远端写入或异步任务已经成功。
- 不能用空数组、空对象、默认值、旧数据或捕获后不处理来掩盖真实失败。

### 可扩展性

可扩展代码允许新增真实业务变化时，优先在既有前后端边界内局部演进。

适用要求：

- 稳定业务规则、协议适配、权限判断、数据访问和外部服务调用应有清晰边界，新增同类能力时优先复用这些边界。
- 公共模块只暴露必要能力，不泄漏内部数据结构、第三方 SDK、数据库表结构或页面细节。
- 同一协议、同一外部服务或同一权限模型的适配应集中维护，避免调用方到处拼条件。

### 易维护性

易维护的前后端代码应让后续开发者能快速定位数据来源、接口契约、错误语义、权限边界和验证入口。

适用要求：

- 业务规则、数据转换、错误语义、权限判断和协议适配不能散落在多个页面、路由或工具函数里。
- 复杂前后端流程应拆出可单独验证的输入校验、权限判断、状态流转、外部调用和响应适配步骤。
- 代码中的注释应解释安全边界、接口兼容、失败处理、幂等策略和非显然副作用。
- 修改完成后应能说明影响了哪些调用方、哪些不变式保持不变、哪些测试证明这些判断。

### 安全性

安全代码默认不信任任何外部输入，也不把权限、安全和敏感信息处理交给调用方自觉。

适用要求：

- 身份认证、权限授权、资源归属、租户或组织边界必须在可信服务端或可信边界验证。
- 用户可控内容进入数据库、HTML、URL、日志、Shell、文件路径、模板或第三方 API 前，必须使用对应上下文的安全处理方式。
- 敏感信息必须最小化读取、传递、记录和展示；日志与错误响应默认不包含密钥、令牌、连接串、堆栈、内部路径或未脱敏个人信息。
- 安全校验必须默认拒绝，不能在字段缺失、配置缺失、解析失败或依赖异常时默认放行。
- 涉及权限、支付、删除、发布、审批、导出和管理操作时，必须说明防重复、防越权和审计或可追踪边界。

## AI 编码执行流程

AI 处理前端、后端、TypeScript、API 或安全相关代码时，必须按工程流程输出，而不是直接堆代码。

适用要求：

- 实现前识别：目标行为、非目标不变式、调用入口、数据来源、权限边界、错误模型、测试方式和可能的破坏性兼容影响。
- 设计时明确：模块边界、类型边界、接口契约、状态流转、失败路径、外部依赖、幂等或并发策略。
- 编码时遵守：最小改动、依赖显式、类型收紧、校验前置、错误显式、权限后端兜底、复用项目既有模式。
- 验证时覆盖：成功路径、关键失败路径、边界值、权限不足、重复提交、外部依赖失败，以及直接相关的回归风险。
- 交付时说明：实际改变、直接相关不变式、验证命令和结果、未验证项、剩余风险。

## 伪高级代码禁区

以下写法看起来可能“完整”或“灵活”，但不属于工程级代码。

禁止事项：

- 用 `any`、类型断言、非空断言、可选链堆叠或默认值让错误消失。
- 在前端隐藏按钮或路由拦截后，省略后端权限校验。
- 把所有错误合并成“系统错误”，或把依赖失败伪装成空数据。
- 为了通过测试只改断言、删测试、跳过校验或引入未标明边界的 mock。
- 把数据库模型、第三方 SDK 返回值、页面状态和接口响应混成同一个对象到处传。

## TypeScript 与类型安全

TypeScript 代码应让类型表达真实业务语义，同时承认类型系统不能替代运行时校验。

适用要求：

- 禁止滥用 `any`、`unknown as X`、非空断言、宽泛类型断言和 `@ts-ignore`；确需使用时必须说明边界、原因和验证方式。
- 外部输入、持久化数据、跨服务响应、URL 参数、表单数据、文件内容和环境变量都必须在可信边界做运行时校验。
- 类型命名应表达业务含义和数据状态，避免 `Data`、`Info`、`Obj`、`Temp` 等无法说明职责的宽泛名称。
- 区分输入类型、领域类型、持久化类型和响应类型；不要让数据库模型、接口 DTO 和 UI 状态互相泄漏实现细节。
- 可选字段、空值、缺省值和状态枚举必须有明确语义；不得用 `null`、`undefined` 或空字符串混合表达多个含义。
- 复杂联合类型应使用可辨识字段表达状态，避免调用方靠字段组合猜测对象处于哪个阶段。
- 异步函数的错误、取消、超时和重试语义应在调用边界可见，不能只靠调用方阅读内部实现。
- 公共 API 导出的类型应保持稳定；删除字段、改变字段含义、放宽或收紧必填性都按兼容性影响处理。

## 安全编码

所有来自用户、客户端、第三方服务、文件、数据库和环境变量的数据，在可信边界完成校验前都按不可信输入处理。

适用要求：

- 前端校验只用于交互体验，不能替代后端校验；后端必须校验身份、权限、资源归属、状态机、金额、数量、时间范围、文件类型和大小等关键字段。
- 输入校验优先使用允许列表，并明确类型、长度、范围、格式、字符集和业务约束；校验失败应拒绝处理，而不是修正成默认成功。
- 输出到 HTML、SQL、Shell、模板、日志、URL、文件路径、HTTP Header 或第三方 API 前，使用对应上下文的编码、转义、参数化或白名单机制。
- 认证、授权和会话控制必须在可信服务端或可信边界执行，不能只依赖前端隐藏、禁用、路由拦截或客户端字段。
- 权限判断应同时校验操作人、目标资源、资源归属、组织或租户边界、状态和动作；不能只校验“是否登录”。
- 密钥、令牌、连接串、生产地址和私有凭据不得写入源码、文档、测试快照、日志或提交说明。
- 错误信息和日志不得泄露密钥、令牌、连接串、堆栈、内部路径、权限细节或未脱敏个人敏感信息。
- 安全相关逻辑应集中复用，避免多个入口各写一套认证、授权、输入过滤或敏感信息处理。

## 后端服务

后端代码应围绕清晰的业务边界、可靠的依赖处理和可观测的失败路径组织。

适用要求：

- 依赖必须显式声明并可复现安装，不依赖开发机全局包、隐式运行环境或未记录的本地配置。
- 配置来自环境变量、配置中心或项目约定的配置系统；缺失、格式错误或权限不足应启动失败或显式报错，不得静默使用危险默认值。
- 构建、发布和运行阶段保持可区分；运行时不应依赖源码目录里的临时生成物或手工步骤。
- 数据库、缓存、队列、对象存储、第三方 API 等后端服务按外部资源处理，通过配置接入，并有明确超时、错误分类和降级边界。
- 服务日志应作为事件流输出，保留排查所需上下文；不得用日志替代错误处理，也不得用静默失败换取表面稳定。
- 后台任务、迁移脚本和管理命令应可重复执行或具备防重机制，并明确执行环境、输入、影响范围和失败处理。
- 关键写操作应明确幂等键、事务边界、并发冲突、重试策略和最终结果确认方式。
- 分层边界应清晰：路由或控制器处理协议接入，业务服务处理规则，数据访问层处理持久化，外部适配层处理第三方差异。

## 接口契约

前后端或跨服务接口应先明确契约，再实现代码。契约至少说明资源语义、请求参数、响应字段、必填/可选、空值含义、错误响应和权限要求。

适用要求：

- HTTP 方法、状态码、错误码和响应结构应保持一致；同类错误不要在不同接口里返回不同语义。
- 字段缺失、类型不符、权限不足、资源不存在、状态冲突、速率限制和外部依赖失败应区分处理。
- 错误码属于接口契约，不能随意改名、复用或把所有失败合并成一个“系统错误”；面向用户的错误文案可以变化，但机器可依赖的错误语义应稳定。
- 列表接口应明确分页、排序、过滤和游标语义；客户端不能依赖未声明的默认顺序或后端内部实现细节。
- 新增字段优先做兼容扩展；删除字段、改字段类型、改必填性、改错误语义、改资源路径或改变分页方式，都应视为潜在破坏性变更。
- 写接口应明确幂等、防重复提交、并发冲突和重试语义；支付、发布、删除、权限变更等关键写操作必须能确认最终结果。
- 接口适配逻辑应集中在 API client、adapter、repository 或项目既有等价层；页面、组件和业务服务不应散落解析同一协议。

## 前端工程

前端代码应优先保持组件职责清晰、状态来源明确、交互行为可预测，并完整处理真实用户路径中的加载、空态、错误态和权限态。

适用要求：

- 组件应围绕展示、交互或容器职责组织；复杂业务规则、请求适配和跨页面状态不应全部堆在组件中。
- 能由已有数据推导的状态，不重复存储；必须缓存或冗余时，应明确刷新、失效和一致性策略。
- 表单应同时处理初始值、输入约束、提交中、提交失败、重复提交、服务端校验错误和成功反馈。
- 网络请求应通过项目约定的数据访问层统一处理认证、错误、取消、重试、超时和响应解析。
- 权限控制不能只靠隐藏按钮；涉及真实权限的操作必须由后端再次校验。
- UI 不应依赖后端未声明字段、未声明排序、内部枚举值或偶然返回结构。
- 可复用组件应抽象稳定交互和展示模式，不强行合并语义不同的 UI。
- 用户可见错误应可理解、可恢复；内部错误细节只进入受控日志或监控，不直接暴露给用户。

## 测试与验证

工程级代码必须能被验证。验证结论只能来自实际执行结果，不能来自“看起来没问题”。

适用要求：

- 改动应覆盖对应层级的测试：纯逻辑优先单元测试，接口契约优先集成或契约测试，关键用户路径优先端到端或等价验收。
- 新增或修改权限、数据契约、错误处理、状态流转、金额数量、后台任务、外部集成时，必须覆盖成功路径和关键失败路径。
- 不得通过跳过、删除或弱化测试，缩小必要验证范围，或仅修改断言和期望值来制造通过结果。
- 提交或交付前，应运行能证明本次改动的类型检查、lint、测试、构建或手工验收命令，并读取完整结果。
- 验证失败、无法执行或覆盖不足时，必须显式说明原因、影响、未覆盖项和剩余风险。
- 测试中的 mock、fixture、seed 和本地模拟必须隔离并标明边界，不得冒充真实业务依赖或掩盖失败。

## AI 输出约束

当 AI 负责生成、修改或评审代码时，除遵守本文其他章节外，还必须主动执行以下约束。

适用要求：

- 先识别项目既有架构、调用方式、错误模型、测试方式和直接相关不变式，再提出或实施改动。
- 不通过放宽类型、吞掉异常、返回默认成功、绕过权限、跳过校验、改测试期望或引入 mock 来制造表面完成。
- 发现真实失败、依赖缺失、权限不足、契约不清或验证无法执行时，必须明确暴露，不得伪装成功。
- 如果用户要求“高级、健壮、可扩展、易维护、安全”的代码，AI 必须把这些词拆解为本文的检查项，并在设计、实现和验证中逐项体现。
- 生成代码时应优先给出能落地的模块边界、类型定义、错误模型、校验策略和测试入口，而不是只给出主流程 happy path。
- 代码完成后必须说明实际改变、已核对的直接相关不变式、验证证据、未验证项和剩余风险。
- 不能确认业务语义、权限边界、破坏性兼容影响或需求承接关系时，应停止并请求用户确认。

## 使用方式

- TypeScript、React、Node.js 或全栈功能实现前，优先对照“总目标”“工程级代码检查项”“TypeScript 与类型安全”。
- 安全相关任务优先对照“安全编码”。
- 后端服务、配置、部署和运行问题优先对照“后端服务”。
- 前后端联调、API 新增或变更优先对照“接口契约”。
- UI、页面、交互、状态管理和数据请求优先对照“前端工程”。
- PR、代码评审和交付前检查优先对照“测试与验证”“AI 输出约束”。
