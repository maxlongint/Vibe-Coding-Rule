# 代码设计原则

本文档定义跨前端、后端、脚本和自动化任务通用的代码设计取舍原则。它回答“应该怎样组织代码”，不替代具体技术栈、业务规则、接口契约、工程检查或根目录 `AGENTS.md` 的底线。

涉及 TypeScript、前后端、API、安全、验证或交付细节时，先用本文判断设计方向，再读取《前后端工程级编码规范》核对工程要求。

## 总原则

代码设计优先服务于业务正确、边界清晰、错误显式和可验证。抽象、复用、拆分和配置都应来自真实复杂度，而不是形式上的整洁或对未来的猜测。

实施时按以下顺序取舍：

1. 先保证行为正确、契约清楚、失败可见。
2. 在正确的前提下，选择最简单直接的实现。
3. 当重复代表同一业务知识或稳定能力时，再沉淀公共边界。
4. 不为假想变化提前增加配置层、扩展点、基类或平行架构。
5. 新增代码应符合项目已有命名、目录、调用方式和错误风格。

“高级代码”不是复杂代码，而是在真实输入、真实失败和长期维护中仍然容易理解、验证和修改的代码。

## KISS：保持简单

优先选择读者能快速理解、调用方能稳定依赖、测试能直接覆盖的方案。复杂性只有在解决真实业务问题时才值得引入。

检查项：

- 能用清晰函数或模块表达的，不引入复杂类层级。
- 能沿用现有项目模式的，不新建平行架构。
- 能局部修改完成的，不扩大到无关重构。
- 复杂实现必须能说明它解决的真实问题、影响范围和验证方式。

## YAGNI：不做未被需要的设计

不要为未来可能出现的需求提前设计。扩展点、配置项、兼容层、通用模块和插件化能力，只有在需求真实存在或已有稳定复用场景时才引入。

检查项：

- 不为一次性需求建立通用框架。
- 不预留没有调用方的参数、分支、接口或配置。
- 不为假想的多租户、多语言、多渠道、多端形态提前改造。
- 如果未来需求出现时再改成本更低，应保持当前实现简单。

## DRY：不要重复知识

DRY 关注知识和规则的重复，不是代码长得像就必须合并。只有语义一致、变化原因一致、抽象后更清楚时，才把重复逻辑沉淀为公共模块。

检查项：

- 同一业务规则、权限判断、校验逻辑、数据转换或协议适配出现多处时，优先评估公共边界。
- 相同校验和错误语义应共享，避免不同入口各写一套。
- 语义不同但结构相似的代码可以保留独立实现，避免隐式耦合。
- 抽象后如果调用方需要大量参数、布尔开关或特殊分支，应重新判断边界。

## 关注点分离

展示、状态、业务规则、数据访问、外部集成、权限校验、错误处理等职责应有清晰边界。跨层协作通过明确接口完成，不直接依赖其他层的内部细节。

检查项：

- 页面或组件不承载大量业务规则、请求适配和数据转换。
- 路由或控制器不堆叠参数解析、权限判断、业务规则、数据访问和外部调用。
- 脚本和自动化任务也应区分输入解析、核心处理、输出呈现和错误处理。
- 公共模块只暴露稳定能力，不泄漏具体页面、接口或第三方实现细节。

## 高内聚、低耦合

模块内部围绕同一职责组织，模块之间通过稳定入口协作。相关逻辑放在一起，不相关模块不互相知道过多实现细节。

检查项：

- 一个模块应能用一句话说明职责。
- 修改模块内部实现时，不应迫使无关调用方同步修改。
- 共同变化的逻辑优先放在同一边界内，变化原因不同的逻辑不要强行合并。
- 文件持续膨胀、职责混杂或修改时总牵连无关逻辑，应重新划分边界。

## 最小惊讶原则

命名、接口、默认行为、错误语义和副作用应符合项目既有习惯和调用者直觉。不要让名称掩盖真实行为，也不要把重要副作用藏在调用方看不见的地方。

检查项：

- 命名表达真实职责，避免 `Data`、`Info`、`Manager`、`Helper` 等宽泛名称滥用。
- 函数、组件和命令不应在名称之外暗含关键副作用。
- 默认值只能表达已确认的业务默认行为，不得掩盖缺失字段、接口失败或权限失败。
- 新增接口和模块应尽量沿用项目已有调用方式、错误风格和目录习惯。

## 使用方式

实施、重构或评审时，先用本文回答四个问题：

1. 当前设计是否保持目标行为正确、非目标不变式不变？
2. 当前复杂度是否来自真实需求，而不是假想扩展？
3. 重复逻辑是否代表同一知识，是否值得抽象？
4. 模块边界是否清楚到可以独立理解、修改和验证？

若答案涉及类型、接口、安全、前后端状态、外部依赖或验证覆盖，再读取《前后端工程级编码规范》继续核对。
