# 最小必要实现规范

> 来源：Vibe Coding Rule 规范包自带文档。接入业务项目后，请保留本标记；业务项目自行新增、生成或沉淀的文档不要使用本标记。

本文吸收 [Ponytail](https://github.com/DietrichGebert/ponytail) 的核心思想，将“少写代码”约束为工程实施前的判断流程。它不要求安装额外工具，也不替代《代码设计原则》和《前后端工程级编码规范》；它只回答一个问题：在不牺牲正确性、安全和验证的前提下，当前需求能否用更小、更现成、更少维护成本的方式完成。

## 适用边界

- 代码实现、缺陷修复、重构、依赖选择、组件选择、脚本和自动化任务。
- 用户抱怨方案臃肿、样板过多、依赖过多、过度抽象或实现路径过长时。
- 不适用于产品口径、业务验收、安全权限和外部状态的擅自缩减；这些内容必须以用户确认的需求事实和唯一需求载体为准。

最小必要实现不是代码高尔夫。目标是减少不必要的拥有成本，而不是为了行数更少而牺牲可读性、边界、错误处理或后续维护。

## 最小必要阶梯

实施前先理解任务和真实调用链，再按顺序停在第一个可成立的层级：

1. **是否真的需要做**：若需求属于未确认的假想扩展、重复能力或无实际调用方的预留，先说明不做或缩小范围的理由。
2. **项目内是否已有能力**：优先复用已有模块、工具函数、类型、组件、服务、错误模型和目录模式，不重新发明邻近代码。
3. **语言或标准库是否已覆盖**：能用标准库、内建类型、运行时能力完成的，不新增自定义实现。
4. **平台原生能力是否足够**：浏览器、数据库、操作系统、框架或协议本身已经提供的能力优先使用，例如原生表单控件、数据库约束、CSS 能力、HTTP 语义。
5. **已安装依赖是否已覆盖**：项目已经拥有且适用的依赖可以复用；不得为了少量胶水逻辑轻易新增依赖。
6. **是否能用局部清晰实现完成**：能用一个清楚的表达式、函数或小模块完成的，不建立框架、配置层、工厂、基类或插件化结构。
7. **最后才写最小可工作实现**：确实没有现成能力时，只实现当前确认目标所需的最小范围，并保留必要的错误、类型、安全和验证边界。

这个阶梯必须在理解问题之后使用。没有读清真实入口、调用方、数据流和失败路径时，不能用“小改动”包装错误位置的补丁。

## 缺陷修复

缺陷报告通常描述的是症状，不一定指出根因。修复前应定位共享入口、调用方和反向路径，优先在根因边界修复一次，而不是在每个表层调用点追加保护逻辑。

检查项：

- 当前修改位置是否覆盖所有同类调用方，而不是只覆盖报错路径。
- 若共享函数、适配层或契约边界缺少校验，优先修复共享边界。
- 若多个调用点语义不同，不能为了少写代码强行合并；应分别保留清楚边界。
- 修复后必须验证至少一个能证明根因被覆盖的路径，必要时补充最小测试或等价自检。

## 依赖与抽象

新增依赖和新增抽象都意味着长期拥有成本。只有它们解决了真实复杂度，且比项目内实现更可靠、更易验证、更易维护时，才值得引入。

少建抽象不等于不要边界。安全校验、接口契约、数据访问、错误处理、外部适配和状态流转仍应有清楚归属；只是优先用项目已有的最轻量表达方式承载这些边界，例如函数、模块、组件、服务、adapter 或 repository。只有真实复杂度需要时，才继续增加接口、工厂、基类、注册器、配置层或插件机制。

默认避免：

- 只有一个实现的接口、只有一个产品的工厂、只有一个值的配置项。
- 为“以后可能会用”提前创建的扩展点、兼容层、插件机制或多端结构。
- 为简单格式转换、轻量状态、少量 UI 行为或一次性脚本新增依赖。
- 为了隐藏复杂度而引入更多间接层，导致调用方需要理解更多开关和特殊分支。

允许引入的常见理由：

- 安全、加密、日期时间、解析器、协议实现、无障碍、国际化、复杂状态机等领域存在成熟且必要的边界。
- 项目已经有同类依赖和调用方式，新增使用不会形成平行技术栈。
- 自行维护的风险、测试成本或兼容成本高于依赖成本，并且已有验证方式能覆盖关键行为。

## 不能省略的内容

最小实现不得省略以下内容：

- 可信边界的输入校验、权限校验、数据契约校验和错误分类。
- 防止数据丢失、重复写入、越权访问、状态错乱和敏感信息泄露的处理。
- 用户明确要求的功能、验收标准、兼容性和可观察行为。
- 用户已确认或项目既有要求中的无障碍基础能力、国际化边界、真实硬件或外部系统校准参数。
- 能证明非平凡逻辑正确的最小验证。

如果为了当前成本做了有意识的简化，并且该简化存在明确上限，应在代码或交付说明中标明边界、影响和未来升级条件。例如全局锁、线性扫描、朴素匹配、固定阈值等，都应说明何时需要替换。

## 输出与交付

实施完成后说明时，应把重点放在实际改变和省略的非必要内容上：

- 实际采用了阶梯中的哪一层能力。
- 跳过了哪些不必要的依赖、抽象、样板或扩展点。
- 已核对哪些直接相关不变式。
- 做了哪些验证；未验证项和剩余风险是什么。
- 若保留了简化实现，说明触发升级的条件。

说明应简短清楚，不用长篇证明“为什么简单”。如果一个方案需要大量解释才能显得合理，通常应重新检查它是否真的简单。

## 与现有规范的关系

- 与《代码设计原则》关系：本文是 KISS、YAGNI 和 DRY 的实施前检查流程。
- 与《前后端工程级编码规范》关系：本文只约束“少建什么、优先用什么”，不降低工程边界要求；类型、安全、接口、权限、错误、数据访问、外部适配和验证仍按工程级规范执行。
- 与 OpenSpec 关系：本文不得改变已确认需求口径。若发现需求本身可能过大，只能提出缩小建议，等待用户确认后再改变验收或实现范围。
